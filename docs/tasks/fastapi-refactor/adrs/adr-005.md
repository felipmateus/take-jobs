# ADR-005: Accent-insensitive search with unaccent + pg_trgm generated column

## Status

Accepted (user approval of the spec, 2026-10-30)

## Date

2026-10-30

## Context

FR-17 requires text search across title, company and description that ignores case and accents. Job text is Portuguese ("Sênior", "migração", "São Paulo"). O7 requires search p95 < 300 ms with 50,000 jobs. The user accepted simple "contains" matching without relevance ranking (PRD Q7; ranking is a Non-Goal).

## Decision

- **Extensions:** migration `0001` enables `unaccent` and `pg_trgm` and defines `immutable_unaccent(text)`, an `IMMUTABLE` SQL wrapper, because `unaccent` itself is only `STABLE` and cannot be used in generated columns or indexes.
- **Search column:** `jobs.search_text` is a stored generated column, `immutable_unaccent(lower(title || ' ' || coalesce(company, '') || ' ' || coalesce(description, '')))`. The `coalesce` is required: `text || NULL` is `NULL`, which would make every job without a company or description unsearchable (review round 1, issue 013), with a GIN `gin_trgm_ops` index.
- **Text query:** `search_text LIKE '%' || immutable_unaccent(lower(:q)) || '%' ESCAPE '\'`, where `%`, `_` and `\` in `:q` are escaped in the repository.
- **Location filter:** the same pattern over an expression index on `immutable_unaccent(lower(location))`.

## Alternatives Considered

### Alternative 1: PostgreSQL full-text search (`tsvector` with the `portuguese` config)

- **Pros:** stemming and ranking.
- **Cons:** word-based. A substring like `pyth` or a company name fragment does not match. Stemming surprises users ("dev" vs "desenvolvedor"). Ranking is out of scope.
- **Why rejected:** does not match the agreed "contains" semantics.

### Alternative 2: Unindexed `ILIKE` with `unaccent()` at query time

- **Pros:** no migration complexity.
- **Cons:** sequential scan plus a function call per row; risky for O7 at 50k rows with long descriptions.
- **Why rejected:** performance target.

### Alternative 3: Normalize in Python and store a plain normalized column

- **Pros:** no extensions.
- **Cons:** two normalization implementations (Python for writes, something else for queries) that must stay identical. Ad-hoc SQL against the table would not match.
- **Why rejected:** a single source of truth inside the database is safer.

## Consequences

### Positive

- One normalization path inside PostgreSQL; literal-safe user input; an indexed substring search.

### Negative

- Depends on PostgreSQL contrib extensions; the official image includes them.
- Trigram indexes add write cost on upsert, which is negligible at about 20k upserts per day.

### Risks

- Queries shorter than 3 characters (`go`, `js`) yield no trigrams. The planner may scan the table or the whole GIN index. IT-011 measures 1- and 2-character queries separately against the same p95 < 300 ms target. If they miss it, the implementer records the measurement and returns to the user before adding a minimum `q` length, because that would change the public contract.
