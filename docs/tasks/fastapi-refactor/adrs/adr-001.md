# ADR-001: Layered package with import-linter enforced boundaries

## Status

Accepted (user approval of the spec, 2026-10-30)

## Date

2026-10-30

## Context

The user required FastAPI "with a layered architecture using dependency injection". v1 mixed HTTP handling, subprocess calls, ORM queries and configuration in the same modules (`controllers/jobs_controller.py`, `app.py`). The product has three entry points: the HTTP API, the collector CLI and the scheduler. All of them must share the same rules (relevance, seniority, activity, run status) without duplication. As a portfolio piece, the architecture must be visible and checkable, not only described.

## Decision

- **One installable package, `take_jobs`, with these layers:**
  - `domain`: pure rules, entities and `Protocol` ports.
  - `application`: use cases that depend on ports only.
  - `infrastructure.db` and `infrastructure.scraping`: adapters.
  - `api` and `cli`: delivery adapters and the composition roots.
- **Dependency injection:**
  - In the API, FastAPI `Depends` chains, built in `take_jobs.api.dependencies`.
  - In the CLI, an explicit composition function.
  - No DI container library.
- **Enforcement:** the import rules in `_spec.md` › Architectural Boundaries become `import-linter` contracts (layers + forbidden) in `pyproject.toml`. `lint-imports` runs in CI.

## Alternatives Considered

### Alternative 1: Separate packages/services per entry point (api, collector, scheduler)

- **Description:** three distributions or images, each with its own copy of the shared models, or a shared library package.
- **Pros:** independent deployability.
- **Cons:** more packaging, more images and versioning overhead for a single-author local project; the shared rules still need one home.
- **Why rejected:** the PRD targets local or self-hosted use with one command. The three entry points can share one image.

### Alternative 2: DI container library (e.g. `dependency-injector`)

- **Description:** declarative containers that wire providers.
- **Pros:** one wiring place for the API and the CLI.
- **Cons:** an extra abstraction on top of FastAPI's native DI; harder for an evaluator to follow.
- **Why rejected:** `Depends` plus one CLI composition function cover both roots with less magic.

### Alternative 3: Convention only (no automated boundary check)

- **Pros:** zero tooling.
- **Cons:** boundaries erode silently; the portfolio claim cannot be verified.
- **Why rejected:** objective O1/O2 favors machine-checked claims.

## Consequences

### Positive

- Use cases are unit-tested with in-memory fakes and no database (coverage target O3).
- A boundary violation fails CI with a precise message.

### Negative

- More modules than a flat FastAPI app. Some mapping code sits between ORM rows, domain dataclasses and API schemas.

### Risks

- Over-abstraction: mitigated by keeping one port per real I/O boundary only (jobs, runs, probe, scraper, clock).

## Implementation Notes

The contracts live in `[tool.importlinter]` in `pyproject.toml`. `import-linter` is a dev dependency.
