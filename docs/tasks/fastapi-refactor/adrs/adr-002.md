# ADR-002: Collection as a three-phase process; Scrapy never touches the database

## Status

Accepted (user approval of the spec, 2026-10-30)

## Date

2026-10-30

## Context

Every collection must:
- record a run;
- relevance-filter, classify and upsert jobs;
- count `new`, `seen_again` and `discarded` per source × term;
- end in `success`, `partial` or `failed`.

The persistence stack is async SQLAlchemy with asyncpg. Scrapy runs on the Twisted reactor, and a Twisted reactor cannot be restarted within a process. In v1, the item pipeline opened its own MySQL connection with hard-coded credentials, created tables, and drove a WebSocket through an improvised `run_until_complete`.

## Decision

`take-jobs collect` runs in three phases:

1. **Start:** `asyncio.run(CollectionService.start_run(trigger, expected_combinations))` creates the `running` run, or refuses (single-running guard).
2. **Crawl:** `JobScraper.scrape(terms)` starts a `multiprocessing` child with the **`spawn`** start method.
   - **In the child:** it ignores SIGINT and runs one `CrawlerProcess` with `TWISTED_REACTOR=None` and `start(install_signal_handlers=False)`. Spiders yield `ScrapedJob`s, and the child groups them into a `ScrapeReport` per source × term, with page counts and errors, then sends the report back through a one-way pipe.
   - **In the parent:**
     - It closes its copy of the child's end right after `start()`.
     - It waits on `multiprocessing.connection.wait([conn, process.sentinel])` and **reads the report before `join()`**. Joining first deadlocks once the report exceeds the pipe buffer: about 64 KiB on Linux and much less on macOS (review round 2, issue 001).
     - EOF or the sentinel without a report means `ScrapeCrashedError`.
     - It never starts a reactor.
   - Scrapy has no item pipeline that does I/O.
3. **Ingest:** `asyncio.run(CollectionService.complete_run(run_id, report))` filters, classifies and upserts, writes the result rows and the final status, all in one transaction.

Failure paths, each followed by `fail_run` in a fresh transaction:
- **Crawl crash:** the child exits without a report → `ScrapeCrashedError`, exit `1`.
- **Ingest exception:** recorded as `ingest failed: …`, exit `1`.
- **SIGTERM/SIGINT:** the parent is the only signal handler.
  - **One handler:** it installs a single `signal.signal` handler for the whole command. It never uses `loop.add_signal_handler`, which resets the signal to its default action when its loop closes (review round 3).
  - **During the crawl:** it sends SIGTERM to the child, which has no Scrapy handlers and terminates at once, waits at most 5 s, then SIGKILLs.
  - **During `start_run` and any `fail_run`:** it only sets the stop flag; these short phases are never cancelled.
  - **During ingestion:** it cancels the task with `loop.call_soon_threadsafe(task.cancel)`, but only before `complete_run`'s commit. The CLI passes `before_commit=phase.clear_cancellable`, and `complete_run` calls it as the last statement inside its `async with uow:` block, after `runs.finish`, so `__aexit__` commits right after it. A cancel already queued when the hook runs can still land during the commit; the re-read covers it. The re-read uses `CollectionService.get_run`. After a cancelled phase, the CLI re-reads the run: if it already finished, it is a late signal.
  - **Between phases:** a stop flag, checked after `start_run` and after the crawl, catches a signal that lands there. After a terminal phase (`complete_run`, or a crash or ingest-failure `fail_run`), a set flag only logs `signal_after_finish`, and the exit code is unchanged.
  - **Outcome:** it records `interrupted by signal`, whatever the child reported, and exits `4` (rule 24).

Each phase that touches the database creates and disposes its own engine.

**Revision after review round 1 (2026-10-30, issues 001, 003, 007).** The first version ran the crawl directly in the collector process and rejected a child process (old Alternative 3) as unnecessary. Review showed this is wrong:
- A second crawl in the same process raises `ReactorNotRestartable`, so tests cannot call `main()` more than once per session.
- A gracefully stopped crawl returned normally and would have been recorded as `success`.

The spawn child fixes both. It also makes `main()` safe to call repeatedly with injected dependencies (`CliDeps`).

## Alternatives Considered

### Alternative 1: Async item pipeline writing each item to the database

- **Description:** asyncio reactor, an `async def process_item` that calls the repository.
- **Pros:** jobs become visible during the crawl; lower peak memory.
- **Cons:** Scrapy's and SQLAlchemy's event loops and lifecycles become coupled. Per-combination counts require shared mutable state across the pipeline and spider signals. A crash leaves half-ingested runs. Pipeline tests need a database.
- **Why rejected:** correctness and testability matter more than early visibility. The peak memory is bounded at about 20k small items.

### Alternative 2: Synchronous SQLAlchemy engine used only by the collector

- **Pros:** a simple blocking pipeline.
- **Cons:** a second repository implementation, or duplicated upsert and filter logic, for the same tables.
- **Why rejected:** it duplicates the persistence code the API already needs.

### Alternative 3: E2E tests run the CLI as a subprocess; the crawl stays in-process

- **Description:** keep the crawl in the collector process; tests call `python -m take_jobs collect`.
- **Pros:** no extra process level in production.
- **Cons:** needs a test-only configuration key so the subprocess can reach the fixture server. Tests cannot inject fakes. The graceful-shutdown problem remains.
- **Why rejected:** the user chose the spawn child on 2026-10-30 (review round 1, issue 001).

### Alternative 4: Fork instead of spawn

- **Pros:** faster start; no re-import.
- **Cons:** forks the parent's state (open sockets, loggers, any imported reactor), and it is unsafe on macOS.
- **Why rejected:** spawn is deterministic across platforms.

## Consequences

### Positive

- Scrapy code is pure: parsing and paging are unit-tested from HTML fixtures.
- Ingestion is tested with a fake scraper and a real database.
- One transaction per completion makes `totals` and `results` consistent (Safety Invariant 3).

### Negative

- New jobs appear in the API only when the whole crawl ends (about 10 minutes).
- If the crawl crashes, or ingestion fails, nothing from that run is stored. The run is recorded `failed` with the reason.
- One extra process start per run, taking about a second to re-import.

### Risks

- R1 (reactor restart and `asyncio.run` interplay) and R6 (pickling across spawn) are covered by IT-007, which runs two collects in one process.

## Implementation Notes

- Spiders keep per-term state: seen ids, pages, a finished flag and an error.
- Errors reach that state through two paths, and both are **mandatory**:
  - **Request errbacks:** `HttpError` → `HTTP <code> <reason>`; `IgnoreRequest` from robots.txt → `blocked by robots.txt`; any other failure, timeouts included → `<ExceptionType>: <message>`, using `type(failure.value).__name__` (review round 4, issue 003).
  - **The `spider_error` signal:** an exception raised inside a callback does not reach the errback. The handler attributes it to `response.meta["term"]`, records `parse error: <ExceptionType>: <message>`, and stops that term's pagination (rule 28).
- The child maps the spider close reason as follows:
  - `finished` → outcomes as recorded;
  - `closespider_timeout` → every unfinished term gets `run time limit reached` (rule 25);
  - any other reason (the child installs no signal handlers, so `shutdown` should not occur) → every unfinished term gets `crawl closed: <reason>`.
- Interruption is decided by the parent alone. Round 2 showed that Scrapy's graceful shutdown waits for in-flight requests, up to `DOWNLOAD_TIMEOUT`. It also showed that a Ctrl+C reaching both processes forces an unclean close with reason `None`. Neither can affect the outcome now.
