# ADR-004: APScheduler container launching the collector as a subprocess

## Status

Accepted (user approval of the spec, 2026-10-30)

## Date

2026-10-30

## Context

The user decided that "a cron job must run the spiders once a day" (RUN_LOG). PRD requirements:
- The schedule and time zone must be configurable (FR-02).
- A collection must run on start when the database is empty, or when no collection finished in the last 24 hours (FR-06, amended 2026-10-30).
- Everything must start with one command (FR-27).

Scrapy's reactor cannot restart, so each collection needs a fresh process. v1 started spiders with `subprocess.Popen(f"scrapy crawl … {search}", shell=True)`, which allowed shell injection.

## Decision

A `scheduler` Compose service runs `take-jobs scheduler`:
- **Scheduling:** an APScheduler 3.x `BlockingScheduler` with `CronTrigger.from_crontab(to_standard_crontab(SCRAPE_CRON), timezone=SCRAPE_TIMEZONE)`, `max_instances=1`, `coalesce=True` and `misfire_grace_time=3600`. `to_standard_crontab` expands the day-of-week field into an explicit Sunday-first list of names (`0-4` → `sun,mon,tue,wed,thu`). This is needed because `from_crontab` numbers days from Monday and rejects name ranges that cross from Sunday, while standard cron starts on Sunday (review issue 016, reopened in round 2).
- **Start-up probe:** the scheduler checks the database with retry and backoff for up to 60 s, logging `startup_probe_failed` on each attempt. It exits `1` if the database is still unreachable; Compose `restart: unless-stopped` restarts it.
- **Startup run (rule 14):** if `SCRAPE_ON_START` is true and `startup_collection_reason(...)` returns a reason, the scheduler immediately launches a collection with trigger `startup`. The reasons are `empty_job_store`, and `no_recent_run` when no run has finished with a `started_at` in the last 24 hours.
- **Launch:** each collection runs as a child process `[sys.executable, "-m", "take_jobs", "collect", "--trigger", trigger.value]`, with `shell=False` (`subprocess.Popen`, kept so a signal can be forwarded).
- **Signals:** the scheduler installs its handler **first**, before the database probe and the startup run, so a stop during the startup collection is forwarded too (review round 3). It handles SIGTERM and SIGINT as follows:
  1. It stops the APScheduler loop.
  2. It sends SIGTERM to a running collector child, which then records its run `failed` with `interrupted by signal` and exits `4`.
  3. It waits up to 25 s, then exits.

  Compose uses `init: true` and `stop_grace_period: 30s`.

The child's exit code is logged. Overlap protection does not rely on the scheduler: the database guard (rule 13) is authoritative.

**Revision after review round 1 (2026-10-30, issues 003, 004, 011, 016).**

APScheduler's in-memory job store recomputes the next fire time on every start. A slot missed while the container was down is never fired, so the original "fires once if back within 1 hour" promise could not hold. **The user decided** on a start-up catch-up instead: collect on start when nothing finished in the last 24 hours. This also covers a laptop that was off at 06:00.

## Alternatives Considered

### Alternative 1: supercronic or system cron in the container

- **Pros:** a standard cron; no Python scheduler dependency.
- **Cons:** an extra binary downloaded into the image. The time zone and the startup-on-empty logic need a wrapper script anyway. Hard to unit-test.
- **Why rejected:** FR-06 and testability favor Python-level control.

### Alternative 2: Host cron calling `docker compose run`

- **Pros:** no scheduler service.
- **Cons:** breaks one-command startup (FR-27) and depends on the evaluator's host.
- **Why rejected:** violates FR-27 and O4.

### Alternative 3: Celery beat with a broker

- **Pros:** a full task system.
- **Cons:** Redis or RabbitMQ plus workers for one daily job.
- **Why rejected:** disproportionate.

## Consequences

### Positive

- Schedule, time zone and the startup run are plain configuration, unit-tested with a fake runner and clock.
- No shell is ever involved (Safety Invariant 6).

### Negative

- One more long-running container.
- APScheduler 3.x is in maintenance mode (4.x is still pre-release).

### Risks

- If the scheduler container is down at 06:00, the cron does not replay the slot. The next scheduler start collects, provided nothing finished in the last 24 hours (rules 14–15). A host that never restarts the scheduler misses the day, which is visible in the run history and counts against O5.
- A start-up catch-up and the 06:00 cron can overlap, for example after a start at 05:59. The database guard (rule 13) refuses the second run with exit `3`, and the run already in progress covers the day.
